# LM-QASAS 日本語解説書

この文書は、「何をするソフトか」「何を根拠に候補を選ぶか」「どの条件で実行したか」を、後から読み直せるようにまとめたものです。最初は1〜5節で考え方を、実行時は6〜7節を、作業を再開するときは8〜10節を参照してください。

本書の対象は、**1人分のPre・Peak・Postを解析するK-means版のコマンド実行エンジン**です。コマンド実行とは、画面のボタンではなく、PowerShellに命令を入力して動かす方式です。GUI、共通UMAP画像、k-NN版、複数人のDB統合は別の開発段階です。実装・検証の最新状態は[README](../README.md)と[開発記録](DEVELOPMENT_LOG.md)を確認してください。

## 1. 最初の目的と、その先のQASAS

最初の目的は、同じ人の3時点のBCRレパトアから、抗原応答に関連する可能性があるCDR-H3配列を順位付けし、希望する種類数を取り出すことです。

```text
1人分の Pre / Peak / Post
    ↓ 入力の検査・cloneの整理
CDR-H3をAbLang2で480次元の数値に変換
    ↓ 3時点をまとめてK-meansで分類
clusterごとのPre・Peak・Postのclone数を比較
    ↓ Peakに存在する候補へスコアを付ける
重複しないCDR-H3を、指定したN種類まで選択・保存
```

将来は、この処理を複数人に行い、候補配列をQASAS用の擬似参照DBへ統合します。5人から各1,000種類なら延べ5,000件ですが、人と人の間に同じ配列があれば、重複除去後は5,000種類未満になります。DB統合の形式や由来の保持方法は、その段階で実装・確認します。

ここで得るものは**実験などで検証する候補**です。順位が高いだけでは、その配列の抗原結合能・中和能は確定しません。とくに、抗体の重鎖・軽鎖の組合せや全可変領域をCDR-H3だけから復元できるわけではありません。

## 2. 「1行」「clone」「1種類」は別の単位

入力は、すでに配列や遺伝子の注釈が付いたCSVです。raw FASTQからV/D/Jを注釈する処理は含みません。Pre・Peak・Postは利用者が指定し、ファイル名の数字から自動判断しません。

| 用語 | このプロジェクトでの意味 |
| --- | --- |
| 入力行 | CSVの1行。検査後も元ファイル・元行への対応を残す |
| clone | V遺伝子・J遺伝子・CDR-H3・isotypeの組合せで区別する単位 |
| clone観測点 | 各時点のunique clone。3時点に同じcloneがあれば各時点に1点ずつ存在する |
| embedding | AbLang2で1配列から作る数値表現。同じ配列の計算結果は再利用できる |
| Top Nの1種類 | 重複しないCDR-H3アミノ酸配列1つ。ユーザーが指定する出力単位 |

たとえば、同じCDR-H3を持つcloneがPeakに3つあっても、V/J/isotypeが違えば解析では3点です。出力ではそのCDR-H3を1種類として数え、3つのcloneの由来を残します。**計算の再利用のための配列重複除去と、解析点の統合を混同しません。**

Countsは元の値を保持しますが、各cloneをCounts回複製したり、密度の重みに使ったりしません。Countsの単位を、未確認のままread数・UMI数と呼ぶこともしません。

入力検査では、必要な列、配列の文字と長さ、注釈の有無・形式などを確認します。今回の暫定条件では、Typeが`WithConserved_NoStop`に完全一致する行を採用候補とします。Typeはisotypeではありません。V/Jのallele表記を外してgene単位にそろえ、複数候補は先頭だけを選ばず、候補の集合として保持します。Csegはsubclassを残して使います。いずれも元の列の文字列を変更せず、clone keyの作成時に適用します。具体的な採用条件・除外理由は[入力規則](INPUT_RULES.md)と各runの入力監査を参照してください。

入力表に十分な根拠がなければ、論文にあるfunctional V/D/Jや全VDJの読み枠などを検証済みとは表示しません。CDR-H3の文字が適切であることだけで、論文の全filterを満たしたことにはなりません。

## 3. AbLang2は何をしているか

AbLang2は、抗体配列を扱うために学習されたモデルです。このプロジェクトでは、公開されている学習済みモデルへCDR-H3アミノ酸配列を入力し、1配列につき480個の数値を得ます。これをembeddingと呼びます。

480個の各数値に「抗原Aへの反応性」などの決まった名前が付いているわけではありません。配列を数値空間で比較するための表現です。**AbLang2単独が、今回の抗原への結合を判定する構成ではありません。** その後で、3時点の分布変化を利用して順位を付けます。

モデルはローカルに取得して、このPC上で呼び出す構成です。モデルの初回取得には通信が必要ですが、配列解析に外部の推論APIを使う設計ではありません。ここでの解析は、ユーザーの配列を使ってAbLang2を追加学習する処理ではありません。Codexなど外部サービスのアカウント設定・データ保持方針は、ローカル解析の設定とは別です。

現在はAbLang2 0.2.1のpairedモデルを基準とします。重鎖側へCDR-H3を渡し、軽鎖側は空にします。pairedというモデル名は、今回の入力に重鎖・軽鎖の実測ペアがあることを意味しません。配列全体を1本のベクトルにまとめる処理をpoolingといい、今回の実装は公式`seqcoding`の特殊トークンを含む平均を明示して用います。最新論文の厳密なpooling・checkpointとの一致は要確認です。「480次元だった」だけで、元論文と完全に同じ解析を再現したとは判断しません。[詳しい確認記録](ABLANG2_NOTES.md)、[AbLang2公式](https://github.com/oxpig/AbLang2)

## 4. K-meansと候補スコアを読む

K-meansは、数値空間にある点をK個のclusterに分ける方法です。Pre・Peak・Postの点をまとめて分類するため、3時点を同じclusterの枠組みで比較できます。ここで使う点は、元の480次元embeddingです。

cluster Cのスコアは、最新論文の式を基準に次で求めます。

```text
S(C) = n_peak(C) / (n_pre(C) + ε)
     + n_peak(C) / (n_post(C) + ε)
```

nはそのclusterに属する各時点のunique clone数です。ε（epsilon）は分母が0になるのを避けるための値で、今回の暫定値は1です。頻度への変換やCountsによる重み付けは加えていません。

次は説明用の架空の例です。実際の被験者データではありません。

| cluster | Preのclone数 | Peakのclone数 | Postのclone数 | ε=1でのスコア |
| --- | ---: | ---: | ---: | ---: |
| A | 5 | 20 | 4 | 20/6 + 20/5 = 約7.333 |
| B | 10 | 15 | 9 | 15/11 + 15/10 = 約2.864 |
| C | 0 | 4 | 0 | 4/1 + 4/1 = 8 |

AはBより高いスコアになります。一方、CはPeakのclone数が少なくても、Pre/Postに観測されないためAより高くなります。εは単なる表示設定ではなく、このような候補の順位に影響し得る解析条件です。

この式は**2つの比の和**です。「PeakがPreとPostの両方より必ず多い配列だけを選ぶ」という判定式ではありません。また、スコアはcluster内の変化を表すので、そのclusterのすべての配列について同じ生物学的挙動を実証するものではありません。

高スコアclusterに属する**Peakのclone**を候補として並べ、最後にCDR-H3を一意化します。同じCDR-H3に複数scoreがある場合は最大値を採用し、全由来cloneを保持します。同点はCDR-H3の辞書順で並べ、N件の境界に同点があればその情報を残します。同点内の順位に生物学的な優劣の意味はありません。[選択部品の規則](SELECTION.md)

300・500・1,000、または任意の正整数を指定できます。候補がN種類に足りなければ、得られた候補だけを出力し、不足数を示します。複製で件数を埋めることはしません。

## 5. 論文の条件と、今回の暫定条件

最新論文・ポスターを主資料とし、古い修士論文は補助資料として扱います。旧KDE/階層クラスタリングの方法を、今回のK-meansへ混ぜません。[資料の対照表](SOURCE_COMPARISON.md)

主資料の論文は、Masuda et al., *LM-QASAS: reference-free identification of antigen-specific sequences from the BCR repertoire using antibody language models*, Frontiers in Immunology (2026), [DOI: 10.3389/fimmu.2026.1844788](https://doi.org/10.3389/fimmu.2026.1844788)です。

| 条件 | 区分と意味 |
| --- | --- |
| CDR-H3入力・480次元・cloneを等重みで扱う | 最新論文を基準にする |
| K-meansのK=500 | 論文の主要設定。今回の対象でも最適だと確認された値ではない |
| 上記の比の和によるスコア | 最新論文の式を基準にする |
| ε=1 | 元論文の厳密な値は要確認。今回の暫定値 |
| seed=20260919、n_init=10 | 同じ条件で比較しやすくするための暫定値。論文記載の値とは呼ばない |
| K-means++、Euclidean距離、Lloyd法、スケーリングなし | 今回の暫定実装条件。元論文の厳密な実装との一致は要確認 |
| 公式seqcodingのpooling | 今回の実装条件。元解析との同一性は要確認 |
| Csegのsubclass保持・複数V/J候補の保持 | 情報を勝手に捨てないための暫定判断。元解析の正規化との一致は要確認 |
| Top Nを異なるCDR-H3で数える | ユーザーとの合意 |
| 最大score・同点の辞書順・不足数表示 | 出力を追跡可能にするための暫定実装規則 |

seedは乱数の開始条件、n_initはK-meansの初期化を試す回数です。これらを固定しても、OS・ライブラリ・計算方式が変われば完全に同一の数値になるとは限りません。各runで環境と条件を保存します。

現在のK-means実装にはscikit-learn 1.9.1を使用します。ライブラリの引数の意味は[scikit-learn公式KMeans文書](https://scikit-learn.org/stable/modules/generated/sklearn.cluster.KMeans.html)を参照できます。公式文書はライブラリの説明であり、元論文の未記載設定を確定する資料ではありません。

論文のK=500は、既知抗体DBとのoverlapを用いた条件選定に基づきます。今回の候補抽出自体には既知抗体DBを入力しませんが、論文の条件選定にも既知DBを使っていない、という意味ではありません。

将来作るUMAP図では、480次元の点を2次元へ配置し、3時点を共通の座標・表示条件で比較します。**UMAP図の近さや見た目の密度から候補スコアを再計算しません。** UMAPは高次元の関係を完全には保存しないためです。論文図の「既知DBに似る配列」の印と、アプリの「選んだ候補」の印も区別します。共通UMAP画像は、本書のCLI追加段階では未実装です。

## 6. 実行と、出力数だけを変える操作

まず[環境の準備](SETUP.md)を行い、モデルを取得します。以下はプロジェクトのルートを開いたPowerShellで使う形式です。入力パスとsubjectは**架空の例**なので、ご自身のローカルファイルと識別名に置き換えます。subjectには本人氏名ではなく、解析用の仮名を使います。

```powershell
$env:PYTHONUTF8 = '1'
& .\.venv\Scripts\python.exe scripts/run_analysis.py `
  --pre 'C:\analysis-input\pre.csv' `
  --peak 'C:\analysis-input\peak.csv' `
  --post 'C:\analysis-input\post.csv' `
  --subject 'S001' `
  --top-n 1000 `
  --clusters 500 `
  --epsilon 1 `
  --seed 20260919 `
  --n-init 10 `
  --batch-size 32 `
  --threads 4
```

`--top-n`は最終出力の種類数、`--clusters`はK-meansのKです。この2つは別の設定です。`--batch-size`はAbLang2で一度に処理する配列数、`--threads`はCPU計算の並列数です。利用可能な引数は`--help`で確認できます。

結果は既定でプロジェクト内の`outputs/`へ保存します。必要なら`--output-root`で親フォルダーを指定できますが、入力CSVのフォルダー内や、既定の原本・資料・`models`・`.venv`・`.git`という保護フォルダー内には保存できません。別名のカスタムモデル保存先まで自動で判別する機能ではないため、結果には専用フォルダーを使います。モデルの場所は`--model-dir`で指定でき、既定は`models/ABLANG-2-paired/`です。この解析コマンドではモデルをダウンロードしません。

入力の種類数・観測数・異なるembeddingの数が指定Kに足りない場合は停止します。Kを自動で小さくして続行することはありません。Kを変更する場合は、その理由と新しい値を明示して再実行します。

途中の警告・除外・件数不足がある場合は、件数だけを見ずに入力監査と実行記録を確認します。処理が停止したrunを完成した結果として使わず、原因を確認した後に別runとして再実行します。入力を直接修正してエラーを回避する運用にはしません。

同じスコアから1,000種類ではなく500種類を選び直す場合は、保存済みのrunを指定します。

```powershell
& .\.venv\Scripts\python.exe scripts/reselect_candidates.py `
  --run-dir '.\outputs\run_YYYYMMDDTHHMMSSffffffZ_ID' `
  --top-n 500
```

この例のrun名は説明用です。実際には初回実行の`Results saved:`に表示されたフォルダーを指定します。

この操作ではAbLang2とK-meansを再計算せず、保存済みPeakスコアから再選択します。元runの状態が`completed`で、`scored_peak.json`のSHA-256が保存時と一致した場合だけ実行します。結果は`selection_500_日時_ID/`のような別フォルダーへ保存し、以前の候補一覧を上書きしません。入力、filter、モデル、pooling、K、εなどを変える場合は、Top Nの変更とは別なので新しい解析runを作ります。

## 7. どのファイルを見ればよいか

runごとに`outputs/run_日時_ID/`を作ります。日時はUTCで、末尾に識別用の文字列を付けます。各ファイルは同じrunの組として保存してください。

| ファイル | 読み取る内容 |
| --- | --- |
| `input_audit.json` | 入力の検査結果、採用・除外理由、原本との対応 |
| `clones.json` | 解析に使うcloneと時点、入力行の由来 |
| `embeddings.npy` | AbLang2の数値表現。人が直接読む表ではなく解析用ファイル |
| `embedding_sequences.json` | embeddingの行とCDR-H3の対応 |
| `cluster_labels.npy` | `clones.json`と同じ行順のcluster ID |
| `cluster_scores.csv` | clusterごとの3時点のclone数とスコア |
| `scored_peak.json` | CDR-H3の一意化前の、採点済みPeak clone候補 |
| `run_metadata.json` | 解析条件、環境、実行状態、コード・入力・出力のhash、初回選択の集計 |
| `selection_initial/candidates.csv` | 初回選択の順位・CDR-H3・score・対応clone数・cluster IDs |
| `selection_initial/candidate_provenance.json` | 候補がどのclone・元行から来たかの詳細 |
| `selection_initial/selection_summary.json` | 指定数・利用可能数・出力数・不足数・境界同点 |

再選択でも、3つの候補ファイルを新しい`selection_N_日時_ID/`に作り、参照したrun・スコアのhash・コードを`selection_source.json`に記録します。CSVには任意の元入力文字列を展開せず、subject、V/J、isotype、入力ファイル・元行、元のCountsやFrequencyなどはJSONの由来情報で確認します。

`run_metadata.json`には、初回選択のサブフォルダーを含む生成済み成果物のSHA-256を保存します。再選択で照合するのは`scored_peak.json`です。保存したhashを使ってすべてのファイルを自動で再検証する機能ではありません。run作成後に生じた失敗は`status: failed`として記録します。入力検査など、runフォルダーを作る前に停止した場合は、runの記録自体が作られないことがあります。

結果を見る順序は、実行記録 → 入力監査 → clusterスコア → 候補一覧 → 必要に応じて由来の詳細、を基本にします。CSVの候補数だけで、前処理や実行が正しかったと判断しません。

## 8. 原本と研究データを守る仕組み

ユーザー提供のデータ・資料は読み取り専用として扱い、削除・移動・改変・上書きしません。正規化やfilterは読み込んだ後の解析用データに適用し、元の値と対応を残します。必要な検証では実行前後のSHA-256を照合し、内容が変わっていないことをローカルに記録します。

| 保存場所 | 用途 | 公開GitHubへの登録 |
| --- | --- | --- |
| `src/`・`scripts/`・`tests/` | コードと人工データのテスト | 内容を確認して登録 |
| `docs/` | 手順・判断・検証範囲の説明 | 研究データを含めず登録 |
| 提供データ・提供資料のフォルダー | 保護する原本 | 登録しない |
| `outputs/` | 実配列・候補・embedding・図など | 登録しない |
| `local_records/` | 個人別監査・入力hash・詳細な検証記録 | 登録しない |
| `models/`・`.venv/` | モデル・実行環境 | 登録しない |

各runと候補選択フォルダーには、内部のファイルをGit登録から除外する`.gitignore`も作ります。`--output-root`で既定以外の出力先にした場合も同様です。再選択時にも保護フォルダーへの書き込みを確認します。

`.gitignore`は誤登録を防ぐための補助で、暗号化や外部送信の全面禁止を行う仕組みではありません。commit前に、登録対象一覧と差分を必ず確認します。実配列や個人別の結果を、GitHubのIssue・PR本文・スクリーンショットへ貼り付けないことも必要です。現時点ではGoogle Driveへアクセスしません。

## 9. GitHubで振り返る方法と、文書・コードの対応

GitHubはコードの保管場所であると同時に、「いつ、なぜ、どこを変えたか」の記録です。主な用語は次の意味です。

| 用語 | 意味 |
| --- | --- |
| branch | 作業の枝。`main`は基準となる枝、開発用branchは機能を追加するための枝 |
| commit | ある時点の変更を記録した単位。識別番号から過去の状態を参照できる |
| PR（Pull request） | 変更内容・理由・検証結果をまとめ、基準となる枝への取り込みを確認する場所 |
| merge | PRの変更を取り込む操作。公開したPRが自動でmainに入るわけではない |

GitHubの`main`は、PRがmergeされるまで新機能を含まない場合があります。「mainを開いたら新しいファイルが見えない」ときは、[Pull requests一覧](https://github.com/YoheiFunakoshi/LM-QASAS-No.1/pulls)から今回の開発段階を開きます。

1. PRの説明で、問題・実装範囲・検証結果・未完了事項を読む。
2. `Files changed`で変更を確認する。
3. 本書を通常の表示で読むには、リポジトリのbranch選択でPRのhead branchへ切り替え、`docs/GUIDE_JA.md`を開く。
4. 過去の特定版を見るときは、commitのリンクからその時点のファイルを開く。

準備段階の[PR #1](https://github.com/YoheiFunakoshi/LM-QASAS-No.1/pull/1)はCPU環境とAbLang2最小試験、[PR #2](https://github.com/YoheiFunakoshi/LM-QASAS-No.1/pull/2)はCDR-H3一意化とTop N指定を扱います。次のPRが前の作業branchをbase（比較元）としている場合、差分には追加分だけが出ます。元の機能が消えたわけではありません。各PRのbase、head（変更した枝）、merge状態を確認してください。

## 10. 後日再開するときの確認手順

1. READMEと開発記録で、前回の完了範囲と未実施事項を確認する。
2. `git status --short --branch`と`git log -5 --oneline`で、実際のbranch・commit・未保存の変更を確認する。
3. 前回の`run_metadata.json`を開き、入力3時点、モデル、pooling、K、ε、seed、n_init、Top Nを確認する。
4. 原本を編集せず、使用する入力とそのhashが前回と一致するかを必要に応じて確認する。
5. 環境・モデルを変えた場合は準備手順とテストを確認し、以前の結果に上書きせず新しいrunを作る。
6. 件数だけを変えたいのか、解析条件を変えたいのかを区別して、再選択または新しい解析を実行する。
7. 結果と未確認事項をローカルに保存し、公開可能な手順・コード・判断・検証範囲をGitHubへ記録する。

テストが通ること、実データで処理が完走すること、候補の生物学的妥当性を検証できることは、それぞれ別の確認です。開発記録では、どの段階まで確認できたかを明記します。
