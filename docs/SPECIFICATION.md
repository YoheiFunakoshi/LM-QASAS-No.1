# 仕様と科学的な前提

## 1. 目的と開発範囲

最初のソフトは1人分のPre・Peak・Postを対象とし、AbLang2による数値化・進捗表示・可視化と、指定数の候補抽出・一覧表示・保存を行います。ユーザーが段階ごとに内容を理解・相談できるように開発します。

複数人の候補を統合するQASAS用擬似参照DBは最終的な利用目的です。複数人統合、QASASでの照合・時系列追跡、raw FASTQからのVDJ注釈処理は、最初のソフトの範囲には含めません。ポスターのASPOによる配列生成も今回の対象ではありません。

## 2. 入力

処理済みレパトア表を、CPM CSV（`.csv`）または対応するタカラ／RGレポートExcel（`.xlsx`）で読み込みます。3時点は同じ形式でそろえ、混在は受け付けません。拡張子で読込処理を選び、内容を検査します。

CPM CSVの列と既存の採用条件は維持します。次の表はCPM CSVの仕様です。

| 列 | 入力上の役割・留意点 |
| --- | --- |
| Vseg | V遺伝子の注釈。暫定実装ではalleleを除き、複数候補を集合として保持 |
| Jseg | J遺伝子の注釈 |
| CDR3 | AbLang2へ渡すCDR-H3アミノ酸配列 |
| AAlength | 記載されたアミノ酸長。実際の配列長と検証する |
| NTlength | 記載された塩基長。これだけで全VDJの読み枠を証明しない |
| Type | 品質・状態ラベル。isotypeとして扱わない |
| Cseg | 明示対応表でsubclassを保持。元論文と同じ粒度かは要確認 |
| Counts | 元の値を保持する。単位を未確認のままread数・UMI数と断定しない |
| Frequency(%) | 元の頻度情報を保持する |

ExcelはRepertoire GenesisのHuman IGHレポート `hIGH20181210` の対応レイアウトに限ります。先頭の `PRINT_hIGH` と2枚目の `Back_data`、レポート名・版・配置を確認し、`Back_data!G:Q` の全データを1行目から読みます。ヘッダー行はなく、`T:AA` の上位50件ランキングを全レパトアとして扱いません。保存されたシート寸法を読み直しの上限に使わず、全データのread数とunique数をレポート集計と照合します。列の対応と厳密な検査条件は[Excel入力の規則](TAKARA_INPUT.md)に記載します。

Pre・Peak・Postの対応はユーザーが指定します。ファイル名の番号やレポートの報告日を採血時点と自動解釈しません。subjectと元ファイル・元行を追跡できる情報をローカル出力に残します。Excelでは元シート名も保持します。

任意列マッピング、別レイアウトのExcel、すべてのタカラ製品・RGレポートへの一般対応は含みません。

## 3. cloneとAbLang2

資料の論文ではV gene・J gene・CDR-H3アミノ酸配列・isotypeの4項目が一致する群を同一cloneとします。各時点のunique cloneを1点として扱い、Countsによる複製・密度の重み付けは行いません。

同じCDR-H3でもV/J/isotypeが異なるcloneは別の観測点です。同じcloneが異なる時点に出現する場合も、各時点の観測を保持します。embedding計算のキャッシュとclone観測の統合を混同しません。

AbLang2へ入力するのはCDR-H3アミノ酸配列のみです。論文で記載されたembedding次元は480です。モデルの版・checkpoint・pooling方法・device・dtype・batch sizeを確定し、実測した形状と合わせて記録します。480次元になることだけで元解析と同一の表現だとは判断しません。

## 4. 前処理

論文にはfunctional V/D/J、in-frame、stopなし、ORF/pseudogene除外、CDR-H3長5未満の除外が記載されています。入力表にない情報について、検証済みと表示してはいけません。

元ファイルを編集せず、除外・変換を行う場合は理由、対象件数、元行への対応をローカルログへ残します。ファイル名からisotypeを強制したり、複数遺伝子候補から無断で先頭だけを採用したりしません。

CPMは既存の`Type=WithConserved_NoStop`、AA/NT記載長などの条件を使います。Excelの新規解析は `takara-rg-hIGH20181210-v2-ignore-d` とし、入力元の`frame=in-frame`とV/Jの機能ラベル`F`への完全一致、標準20アミノ酸・長さ5以上、有効なV/J注釈、単一に決まるC subclassを採用条件とします。Excelのコンマ区切りV/J候補は未解決の集合として保持し、alleleを外しても複数subclassが残るC注釈は除外します。Dの注釈・機能は採否にもclone keyにも使わず、生の元情報を保存します。Dを含む供給元集計との照合はファイル整合性のために維持します。C機能ラベルも元情報として保存しますが、`F`条件は追加しません。

ExcelのCDR3は入力どおりに保存し、末端C/Wの追加・削除、CPMのTypeへの置換、NT配列・NT長・全行のFrequencyの補完は行いません。機能ラベルと読み枠は供給された注釈への条件であり、独立した再注釈や全VDJの機能性検証ではありません。形式間のCDR3境界定義の同等性も未確認です。両形式で`full_vdj_functionality_verified=false`を記録します。

## 5. 解析と候補抽出

初期実装ではK-means版から検証する方針です。k-NN版はその後に検証します。

K-means版では、1人の3時点のembeddingをまとめてクラスタリングし、clusterごとに次のスコアを計算します。

S(C) = n_peak(C) / (n_pre(C) + epsilon) + n_peak(C) / (n_post(C) + epsilon)

各nはその時点・clusterのunique clone数です。比の和であり、「両方の比が閾値以上」という条件を追加する場合は別の方法変更として記録します。論文では高スコアclusterに属するPeak時点の配列を候補とします。

論文の主要設定はK=500です。k-NN版の主要設定はk=200で、480次元空間のcosine distanceに基づく第k近傍距離の逆数を密度proxyとして用います。これらは論文でCoV-AbDabとのoverlapによるgrid searchで選定された値であり、新しい対象に対する最適性を確認した値ではありません。

候補抽出時に既知抗体DBを必要としないことと、論文の条件選定・評価で既知DBを使っていないことは同義ではありません。

実装ではepsilon=1.0、seed=20260919、n_init=10、K-means++/Lloyd法・Euclidean距離・スケーリングなしを暫定採用しました。元条件との一致やk-NNの自己点・距離ゼロなどは[決定記録](DECISIONS.md)を参照します。全配列間の巨大な距離行列を無条件に作成しません。

## 6. 可視化

3時点の全clone観測をまとめた共通UMAPと、共通格子・帯域幅・色スケールの時点別KDEを実装しました。各時点の密度は格子上の積分が1になるよう正規化し、Countsで重み付けしません。Peakから選んだCDR-H3が各時点に出現する位置をオレンジで示します。候補数変更は同じ座標と背景密度を再利用します。既定値と限界は[可視化の説明](VISUALIZATION.md)に記載します。

**候補スコアは元の高次元embedding空間で計算し、UMAP座標から計算しません。** 2次元の密度図は理解のための表示です。論文図の既知DB類似配列の印と、アプリが抽出した候補の印を混同しない凡例にします。

## 7. 出力

候補数は300・500・1,000の選択と任意の正整数入力に対応します。Top Nはユーザー合意により、重複のないCDR-H3アミノ酸配列の種類数とします。100も任意指定できます。

候補一覧にはrank、subject、timepoint、CDR-H3、V/J、isotype、score、cluster ID、embeddingへの対応、source file/rowへの対応を保持します。同じCDR-H3を出力段階で集約し、元のclone情報と採用スコアの根拠を保持します。[候補選択部品](SELECTION.md)では最大score、同点の辞書順、不足の明示を暫定規則として実装しました。

GUIまたはCLIで候補CSV、由来JSON、embedding/cluster labelsのNPY、clusterスコアCSV、入力監査・実行条件JSONを出力します。候補CSVは順位・CDR-H3・score・clone数・cluster IDを持ち、V/J/isotype・subject・全元行・生の元フィールドは由来JSONに保持します。可視化時は共通座標NPY、密度NPZ、PNG、表示条件JSONも別の新規フォルダーへ保存します。Excel専用出力は未実装です。

同じ解析スコアからTop Nだけを切り替える際はAbLang2を再計算しない設計です。旧runの入力policyも変えません。Dの採否条件を変えて候補を得るには新しい解析が必要で、旧runはそのまま保持します。

## 8. 実装段階

1. 環境確認とAbLang2最小動作確認：まず模擬配列でimport、device、embeddingの形状・有限値・再実行を確認し、結果をユーザーへ報告。
2. 入力検証・前処理・K-means・ranking・CSV出力をCLIから検証。
3. 共通UMAPと候補の可視化を検証。
4. 安定したエンジンを呼び出すGUIを作成し、1人分のアプリを完成。
5. 必要に応じてk-NN等を追加し、複数人の候補からQASAS用DBを作る段階へ進む。

解析エンジンとGUIは分離します。研究用の検証可能性・再現性を優先します。

## 9. 資料の優先順位と実装上の判断

最新論文・ポスターを主資料とし、2025年の修士論文を補助資料とします。[資料対照](SOURCE_COMPARISON.md)に根拠ページ、違い、要確認事項を記録します。旧KDE/HCやread数重みを、今回のK-means/k-NNへ混在させません。

ユーザーから、未確認事項を明示したうえで妥当な実装判断を行う方針が承認されました。暫定値や運用上の選択は論文の設定と区別して記録し、結論への影響や入力の意味を判断できない場合は確認します。

## 10. 現在の実行可能範囲

`run_analysis.py`が入力から候補保存までを実行し、`reselect_candidates.py`が保存済みスコアから件数だけを変えます。入力の暫定条件は[共通条件・CPM CSV規則](INPUT_RULES.md)と[Excel規則](TAKARA_INPUT.md)、仕組み・操作・結果の読み方は[日本語解説書](GUIDE_JA.md)にまとめます。実施済みの動作検証範囲は[開発記録](DEVELOPMENT_LOG.md)を参照します。候補抽出の性能や抗原結合の妥当性を検証済みとは表示しません。

`start_app.py`が127.0.0.1限定のGUIを起動し、別プロセスのworkerが計算と図作成を行います。ブラウザーには進捗・候補表・図・入力検査を表示します。CSV・Excelとも各20 MiB以下、base64を含むJSON送信全体は64 MiB以下です。大きい入力はCLIを使用します。Excel読込自体の上限は[Excel規則](TAKARA_INPUT.md)に従います。`visualize_run.py`から保存済みrunを直接可視化することもできます。
